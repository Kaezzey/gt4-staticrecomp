# M0 — A repeatable experiment

Objective: trace how source becomes an executable and how a test reports success.
Reverse-engineering experiments need repeatable builds so a changed result can
be attributed to a changed model rather than a stale binary.

```text
project.cpp -> gt4recomp_core library -> main.cpp -> gt4recomp.exe
                                   -> project_test.cpp -> test executable
                                                         |
                                                       CTest
```

A translation unit is a source file together with its included declarations.
The header declares `project_name`; the source defines it once. The library
holds that compiled implementation, and the linker connects calls from the CLI
and test to it. This same separation will later let analysis tools and tests
share our decoder without duplicating it.

CMake describes targets and their dependencies. Ninja executes the resulting
build actions. CTest launches test executables and evaluates their outcomes.
The PUBLIC C++20 requirement on the library also reaches consumers.

Worked example: the CLI calls `project_name()`, obtains a `std::string_view`
referring to a string literal with static lifetime, and prints it. The test
calls the same library function and returns nonzero if its identity is wrong.
It uses an explicit condition, so Release builds cannot disable the check as
they could with `assert` under `NDEBUG`.

Prediction: configure should detect MSVC; building should produce a library,
CLI and test; CTest should report two passing checks. The CLI should explicitly
say that guest execution is not implemented.

These checks prove compilation, linkage, execution and test registration. They
prove nothing about GT4 or instruction semantics. This deliberately trivial
test is the build-workflow exercise; later tests must cover actual behavior.

Source is in `src/`, `include/`, `tools/`, and `tests/`. Host artifacts go in
`build/`; original game inputs stay in `iso/` or `private/`; generated game-derived
code belongs in `generated/`. Do not confuse either generated category with
original project source.
