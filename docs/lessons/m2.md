## Objective

Explain how a disc image differs from files inside it, and use a reproducible
fingerprint to reject accidental input changes before reverse engineering.

An ISO is a file containing a disc image. Its filesystem identifies contained
files, including their names and locations. A whole-image digest covers more
than CORE.GT4: filesystem metadata, other files and padding also contribute.
Consequently two images can contain identical CORE bytes but have different
whole-image hashes. This project deliberately pins the complete image too.

SHA-256 maps a byte sequence to a 256-bit digest, printed as 64 hexadecimal
characters. It does not contain a decoded title or revision. We obtain those
claims separately: the owner identifies USA v2.00, and this disc's SYSTEM.CNF
reports version 2.00 and its boot executable. Our hash is an identity check,
not an authenticity certificate.
[Python hashlib documentation](https://docs.python.org/3/library/hashlib.html)

## Implementation map and data flow

- `scripts/gt4disc.py`: inspect the image, parse selected configuration fields,
  fingerprint inputs, validate a baseline and report differences.
- `scripts/requirements.txt`: pins pycdlib 1.20.0 for this observation tool.
- `docs/inputs/usa-v2.00.json`: schema version, disc identity, system metadata,
  and the three contained-file identities. No game payload or absolute path.
- `tests/python/test_gt4disc.py`: original synthetic ISO fixtures and failure tests.

```text
ISO path -> chunked SHA-256 -> compare pinned disc size and digest
                                  |
                                match
                                  v
                  pycdlib locates SYSTEM.CNF
                                  v
             BOOT2 identifies the root boot executable
                                  v
        hash SYSTEM.CNF, boot executable and CORE.GT4 streams
                                  v
                 compare metadata and all fingerprints
```

`fingerprint` consumes at most one MiB per read, accumulates byte count and
updates a SHA-256 object. Reading the complete 5.3 GB image is necessary, but
holding it all in RAM is not. Chunk boundaries do not change the digest.

pycdlib supplies filesystem observation through `open_file_from_iso`; our tool
owns fingerprinting and verification policy. It does not reconstruct or
translate the game's executable. The core recompiler remains C++.
[pycdlib streaming API example](https://clalancette.github.io/pycdlib/example-reading-file-in-chunks.html)

## Worked example

The observed BOOT2 value is `cdrom0:\SCUS_973.28;1`. `read_config` checks the
supported filename pattern, produces ISO path `/SCUS_973.28;1`, and normalizes
the filename to serial `SCUS-97328`. `;1` is an ISO file-version suffix; it is
not GT4's retail revision. The separate VER field supplies `2.00`.

The boot stream has 273,020 bytes. Its SHA-256 begins `f8f10823`; the manifest
and verifier always use the entire digest. CORE.GT4 has 2,020,861 bytes; the
config has 57. We hash raw file bytes, including line endings; parsing text
does not replace the raw config fingerprint.

Prediction: renaming the host ISO leaves every comparison unchanged. Changing
one byte without changing length fails the SHA-256 comparison. The synthetic
tests demonstrate both cases, without altering the real disc.

## Run it

From the repository root, first-time setup (Python 3.10+):

```powershell
python -m venv private/tooling-venv
& '.\private\tooling-venv\Scripts\python.exe' -m pip install -r scripts/requirements.txt
```

The current workspace already has that environment. Normal verification:

```powershell
& '.\private\tooling-venv\Scripts\python.exe' scripts/gt4disc.py verify 'iso/Gran Turismo 4 (USA) (v2.00).iso'
```

To print observations without modifying the baseline:

```powershell
& '.\private\tooling-venv\Scripts\python.exe' scripts/gt4disc.py inspect 'iso/Gran Turismo 4 (USA) (v2.00).iso'
```

Exit codes: 0 means success; 1 means an input/baseline mismatch; 2 means an
input, schema or parsing error. Inspecting successfully does not mean matching
the pinned disc. `verify` never rewrites the manifest. There is no automatic
repin command; changing a baseline is a deliberate reviewable source edit.

## Evidence and limits

Run the standalone tooling tests (not part of CTest):

```powershell
& '.\private\tooling-venv\Scripts\python.exe' -m unittest discover -s tests/python -v
```

12 tests passed: a known SHA-256 vector, chunk-size independence, config
parsing and rejection, repeatability, renaming, same-size mutation without
repinning, truncation, wrong contained hash, missing CORE, invalid manifest,
and missing ISO. Generated test images contain only original fixture bytes.

Real-data verification passed separately. The ISO matches the earlier
PowerShell fingerprint; extracted local copies of all three selected files
also match PowerShell hashes and sizes. This independently checks digest
calculation, but both contained-file paths rely on pycdlib's filesystem parser.

This tool intentionally supports the selected root-level PS2 BOOT2 form and
ISO namespace. It is not a universal disc validator. Inputs must remain stable
while inspected; snapshot isolation against concurrent modification is not
implemented. Whole-image comparison is intentionally strict. The script does
not validate ELF layout, code semantics, provenance or reconstruction-tool
compatibility. C++ behavior was unchanged, so C++ tests were not rerun.
