# M3 — A reference executable and its limits

BUILD/VERIFY completed on 2026-09-13. EXPLAIN remains pending tutoring, as do
earlier checkpoints not explicitly completed by the owner. This milestone
produced a reference artifact, not our own reconstruction tool.

## Objective and worked example

An executable image describes bytes placed at guest addresses. ELF program
headers describe loading; sections organize content for tools. The entry point
is a guest address, not an offset into the file. For a file-backed segment:

```text
file offset = segment file offset + (guest address - segment guest start)
```

The observed entry `0x100008` is eight bytes into text, whose ELF file offset
is `0x1000`. Therefore entry bytes are at file offset `0x1008`. They are at
offset `0x13C` in the inflated CORE body. The original CORE is compressed, so
there is no corresponding simple addition into its compressed stream.

When segment memory size exceeds file size, ELF loading specifies zero-filled
extra bytes. Those bytes need not be stored in the file.
[ELF program-header specification](https://gabi.xinuos.com/elf/07-pheader.html)

## Reference result

PDTools release `elfbuilder-1.0.0` accepted our pinned CORE and reported its
internal authentication check as matching GT4 (US), build value 82101. We did
not independently implement authentication or test GT4Hooks injection.
[Official reference release](https://github.com/Nenkai/PDTools/releases/tag/elfbuilder-1.0.0)

The output is ELF32 little-endian, 6,127,896 bytes, with entry `0x00100008`.
[Reference metadata](../inputs/usa-v2.00-reference.json) records complete hashes,
tool provenance and all compared payload ranges.

| Content | Inflated offset | ELF offset | CORE target | ELF address | Size |
| --- | --- | --- | --- | --- | --- |
| Record 0 / reginfo | `0x114` | `0x519000` | `0x6179FC` | `0x617A14` | `0x18` |
| Record 1 / text | `0x134` | `0x1000` | `0x100000` | `0x100000` | `0x517A14` |
| Record 2 / data | `0x517B50` | `0x519100` | `0x617A80` | `0x617A80` | `0xBE37C` |

All three payloads match in full. Text and data are the two PT_LOAD segments;
REGINFO is supplementary metadata, not a third PT_LOAD segment.

## What changed and why

- `scripts/build_reference.ps1`: checks CORE and builder hashes, refuses an
  existing output, runs the external builder and independently checks its output.
- `scripts/inspect_reference.py`: checks the pinned CORE, inflates it with zlib,
  reads three record descriptors and compares every payload byte with ELF ranges.
  Named fields and explicit offsets make the byte flow traceable. It emits only
  metadata; it is a scoped read-only experiment, not a general ELF validator.
- `scripts/ghidra/VerifyReferenceImport.java`: compares imported PT_LOAD bytes
  with the reference file and reports memory blocks and the entry representation.
- `tests/python/test_reference_inspection.py`: synthetic fixtures for success,
  wrong input, changed payload, wrong entry, truncation and reginfo address shifts.

```text
pinned CORE -> external builder -> reference ELF -> LLVM and Ghidra inspection
     |
     +-> Python zlib -> record payloads -> full byte comparison with ELF ranges
```

Prediction: changing a payload byte must fail comparison even if the ELF still
imports. The synthetic test demonstrates that failure without editing game data.

## External source consultation and unresolved choices

Question: why did the builder move reginfo and add a BSS region absent from its
input log? Our hypothesis was that it synthesized some analysis metadata.
The tagged builder confirms a fixed `0x800000` BSS size and `+0x18` reginfo
address adjustment. Broad text/data labels and permission flags are builder
choices too. We inspected this source, but copied none into our implementation.
[Tagged ElfBuilder.cs](https://github.com/Nenkai/PDTools/blob/elfbuilder-1.0.0/PDTools.GT4ElfBuilderTool/ElfBuilder.cs)

The loader source suggested raw DEFLATE after a six-byte header, then two
length-prefixed authentication values followed by entry/record information.
Python zlib and exact byte comparisons validated that interpretation on this
input using a different decompressor. The record interpretation is informed
by that source, not claimed as independent discovery.
[Tagged GTImageLoader.cs](https://github.com/Nenkai/PDTools/blob/elfbuilder-1.0.0/PDTools.GT4ElfBuilderTool/GTImageLoader.cs)

The data segment declares alignment `0x1000`, but its virtual address remainder
is `0xA80` and file-offset remainder is `0x100`. These do not satisfy ELF's
alignment congruence rule. Ghidra accepting the file does not make that header
conformant. Generated BSS covers `[0x6D5DFC, 0xED5DFC)`; Ghidra models it as
uninitialized. No runtime zeroing has been tested.
[ELF alignment rules](https://gabi.xinuos.com/elf/07-pheader.html)

M4 must not blindly adopt the BSS size, reginfo relocation, alignment or
permissions as hardware requirements. Validate uncertain behavior against the
actual loader or dynamic captures. M3 establishes no boot success or function map.

## Verification and limits

- Two reconstructions produced SHA-256
  `94aada8984999736f14a121ea1bd543e72d9d59b801e513716a32d8991746222`.
- LLVM readelf 22.1.8 independently decoded the ELF tables.
- Ghidra 12.1.3 imported both loadable segments and matched all 6,118,800
  file-backed bytes at their expected guest addresses.
- 18 Python tests passed: the earlier 12 plus six reference-inspection tests.

Ghidra language `MIPS:LE:64:64-32addr` displays the entry as opaque `SPECIAL2`.
The import marker proves byte placement, not correct R5900 decoding. An
R5900-specific language still needs validation before instruction analysis.
No PCSX2 runtime comparison was performed. C++ was unchanged and not retested.

## Repeat locally

The official archive and executable are under ignored `private/reference-tools/`;
their hashes are recorded. The published .NET 6 tool initially failed because
that runtime is absent. Process-local `DOTNET_ROLL_FORWARD=Major` succeeded
with the installed newer runtime; no runtime installation was needed.

From the repository root, use a fresh output filename:

```powershell
./scripts/build_reference.ps1 -Output private/reference-elf/new-reference.elf
python scripts/inspect_reference.py private/fingerprint-check/CORE.GT4 private/reference-elf/new-reference.elf
llvm-readelf --file-header --program-headers --sections private/reference-elf/new-reference.elf
& './private/tooling-venv/Scripts/python.exe' -m unittest discover -s tests/python -v
```

The CORE copy comes from M2 and is checked against the disc manifest. On a new
workspace, first extract it from the verified owned ISO into that ignored path,
and extract the official tool release into
`private/reference-tools/GT4ElfBuilderTool-1.0.0/`.

Ghidra rejected `+` in the repository's parent path for its project location.
The successful project is `%TEMP%/GT4Recomp-M3/GT4-USA-v2-M3.gpr`. Temporary-file
cleanup may remove it; recreate with a fresh project name as follows:

